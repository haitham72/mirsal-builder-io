# The golden path (`flow/gates.py`, checkpoint 1F)

<sub>Part of [engine-and-studio.md](../engine-and-studio.md).</sub>

request -> **G1 plan** -> sheet -> Python blocks bad cells -> **G2 stills** -> **video sheet** from the approved stills only -> **G3** -> returned video attached to `A<n>` -> Python blocks bad slots -> **G4 animations** -> **G5 pack** (approved at G2 AND G4). The rules live in Python and the page only displays them: an out-of-order or illegal action is a `409` whose message is the reason.

- **Python's block is final.** Nobody can approve or reject a `FAILED`/blocked sticker. Rejection never deletes. A sticker keeps its original `S#` (slot n of every video sheet holds `S<n>`).
- **Order and locks.** G2 needs the plan approved (G1), the stills sliced and no active video sheet; the plan decision is locked once a still is decided; stills decisions are locked while a video sheet is not `REJECTED`; the sheet build needs every READY sticker decided and at least one approved; the upload needs the sheet approved (G3) and is allowed again after `VIDEO_BLOCKED`; G4 needs sliced animations; G5 needs every READY animation decided and passes `pack_limits`; animation decisions lock once the pack is approved. "Approve all READY" only touches stickers still `PENDING`.
- **Batches, generations, regenerate (Haitham, 2026-10-08; the flow is {current model} -> {next model}).** A *batch* is a family (`flow/groups.py`: a root and its redos/edits); each member is a *generation* (`generation 01..n`, root first). `groups.family(gid)` answers `{root, picked, members[{id, generation_id, n, relation, stage, ready, sheet_model}]}`; ONE generation per batch is *picked* (`groups.pick`, stored as `picked` + `pick_history` on the root; default: the newest member): it is the one animated. Add to a pack uses the generation currently in view, including an earlier generation. *Regenerate (sheet)* is a new generation of the batch: `POST /api/live/sheet {from_generation, parent, regen_of}` (the batch's own cells and tags, relation `redo`), picked by default when it arrives. *Regenerate (video)* stays inside one generation: `POST /api/live/video {generation, redo: true, video_prompt, model}` -> `gates.redo_video` retires the current video sheet as `SUPERSEDED` (a `VIDEO_BLOCKED` one, which never made clips, is `REJECTED`), copies each clip to `slices/versions/<name>-A<n>.webm` (`sticker.anim_versions[]`), `quick_sheet` builds the next `A<n>` from the same kept stickers and the job sends it with the model and the exact text shown. The video sheets with a video are that generation's *animations* (`animation 01..n`): `gates.cut_sheet` is the one the stickers are cut from (the `SLICED` one, else the latest `SUPERSEDED` while a new one is being made); `gates.pick_video` makes an earlier one current again (re-cut from its stored video, free; G4 asks again); `gates.remove_video` takes one out (`REJECTED`, files kept; the one in use cannot be removed). *Next batch* (the Studio's old "Create more"): `tasks.next_batch(gens)` plans the next UNCLAIMED batch of the batches on screen (every generation of their families counts): a preset emoji pack takes the next unused preset grid, any other request the next nine bank tokens none of them drew (`actions.next_tokens`, `actions.BODY_SENTENCES` / `FACE_SENTENCES`, `prompter.expand(tokens=…)`); a transformation or a finished bank answers `{complete, message}` in words. Nothing is spent until Generate sheet; the sheet joins the session as the next batch. *Several batches in one Generate* (Haitham, 2026-10-09: "1 batch, 2 batches, n batches"): `/api/plan` answers `batches_max` (`tasks.batches_max`: an emoji pack's 4 preset grids = 36 actions, a bank request as many full grids as the bank has left, capped at 4; a transformation or a 1x1 only 1), the Prompt step offers **Batches 1 … n** next to Generate sheet with the total price on the button; the click starts the previewed sheet, then `POST /api/plan/more` (`tasks.more_batches`: the next preset grids, the one shown skipped, else the next unused bank actions 9 at a time) and starts each of those as its own sheet job (each priced and charged on its own; `MIRSAL_PAID_PARALLEL` jobs run at once). They carry one run key (`mode: pack`), so every finished sheet joins the same session as Batch 1 … n. **The buttons are batch numbers of the session, at most 4 in all** (Haitham, 2026-10-09): a new request offers 1-4; a Next-batch draft counts what the session has (`tasks.session_state`: its batches are families, not generations; `/api/plan/next` answers `existing` and `batches_max`), so one batch on screen offers 2-4 and three batches only 4; pressing k makes batches existing+1 … k, `/api/plan/more` gets the session (`gens`) and skips every grid and action it already used, and they join the session on screen (`mode: next`). **An emoji pack counts grids, not screens:** batch k IS grid k (core-v1 = stickers 1-9, social-v1 = 10-18, reactions-v1 = 19-27, daily-v1 = 28-36). `session_state` reads the request without any grid name (`actions.strip_presets`) and gathers the grids of EVERY batch of that request by the same person (the last 300 batches), on screen or not; a following batch is the base request plus the next unused grid's name, and when a request names several grids the last one wins (`actions.preset_name`). (2026-10-09: batch 3 of "original generic emojis, colorful" repeated batch 1: the request still carried "social-v1", "…social-v1 core-v1" was read as one grid and "…social-v1 reactions-v1" as social-v1.) `sheet_model` (batch) and `video_sheets[].model` record what made each result. *The Studio (2026-10-08):* each batch's header is `Batch k` and its generations row `★ gen 1 · gen 2 · …` (the Studio feature scripts (`docs/architecture.md` §6) `gensHtml`; ★ = the main, the one in view filled); the one in view carries **Make main** (`POST …/pick`), **Delete** (to the trash; `groups.hand_over_plan` + `hand_over` keep the others ONE batch: the oldest survivor becomes the root, the main moves to a survivor) and **Report**. The session shows what is in view; Animate uses each batch's MAIN generation; Add to a pack uses the generation in view. The pack wizard defaults to a pack that contains that generation, otherwise New pack; a manual emoji batch uses its explicitly planned target pack. A pack selected for another generation does not become its default. Below it, ONE frame (`sheetPanel(g, mode)`): view tabs Raw · Keyed (· Fixed) · To send · Video over one picture with that view's cell controls on it (design §9), one caption line, and ONE control row (`genRow`): the model as a plain drop-down ("made with X →"), the settings that have a choice, Loop for a video, Generate/Regenerate with the price, and a Prompt toggle. Stickers regenerates the sheet (a new generation), Animation the video (a new animation, at the Gap of the To send view, the only view with the Gap slider). The old two-panel layout, the box under the green screen and the Variations strip are gone; so is the Prepared-sheets chip row. In the Video view the **animations row** (the Studio feature scripts (`docs/architecture.md` §6) `animRow`) lists the generation's animations (`animation 1 … n`, ★ = `cut_sheet`, a removed one leaves the row): a click on another picks it (`POST …/pick_video`), its x takes it out (`POST …/remove_video`, never the one in use), **Report** is a ticket on `G###/A#` (ticket kind `animation`). A batch with a prepared 3x3 video (`source.video_path`) has no row. Each batch header also has **Import picture** (Stickers) / **Import video** (Animation): see "Existing-sheet imports".
  *Video:* `POST /api/live/video {generation, redo: true, video_prompt, model, options}` -> `gates.redo_video` retires the current video sheet as `SUPERSEDED` (a recorded human REJECT with `superseded: true`; a `VIDEO_BLOCKED` one, which never made clips, is simply `REJECTED`), copies each sticker's clip to `slices/versions/<name>-A<n>.webm` (`sticker.anim_versions[]` {sheet, webm, review, ts}), then the usual `quick_sheet` builds the next sheet from the same kept stickers and the job sends it with the model and the exact text the person read. `gates.cut_sheet` (the latest sheet with a sliced video: `SLICED` or `SUPERSEDED`) is where animations come from, so the stickers keep the retired sheet's clips until the new video is sliced; re-slice, reloop and the overrides read it. Refused while a returned video is being cut. *Sheet:* `POST /api/live/sheet {from_generation, redo: true, sheet_prompt, model}` -> `pipeline.resheet_check` before anything is spent, and when the sheet arrives `pipeline.resheet` copies the sheet, keyed sheet, stills, plain twins and clips to `versions/v<n>/` (`sheet_versions[]` with every sticker's status and decisions at that moment), retires every video sheet (`REJECTED`, `retired_by_sheet`: their stills are gone), drops a prepared video, clears G5, resets the stickers to G2 (history kept) and `run_stills` cuts the same batch again. `sheet_model` (on the batch) and `model` (on each video sheet) record what made the current result; the Studio's regenerate strip (Stickers and Animation views, and the Prompt tab) shows the prompt that was sent, the model folded as {current} -> {next} (`live.js modelPick`) and the price on the button. No switcher back to an older version yet (plan Phase 5).
- **`result.json` additions.** `tags` (1-5 per sticker, `tags[0]` = key), `review {still, anim}` (`PENDING|APPROVED|REJECTED|BLOCKED`), `history[]` (`{ts, stage, actor python|human|vlm, decision PASS|BLOCK|APPROVE|REJECT, reason, ref, detail}`; stages `sheet, sliced, still, video_sheet, video, anim, pack`; `detail` carries the failing check's `value`, `limit` and data, e.g. `inside_slot` frame and px over), `reviews {plan, video_sheet{A1}, pack}` (each `{decision, by, ts, note}`; pack also `stickers[]`), `video_sheets[] {id, slots, grid, file, layout, video, status BUILT|APPROVED|REJECTED|VIDEO_RETURNED|VIDEO_BLOCKED|SLICED, verify[], blocked, video_checks[], video_flags[], video_info}`, `verify {sheet[]}`, `template_id/version`, `slots`, `task_id`, `name_key`, `regen_of`. Results written before 1F load with empty versions of these (`pipeline.normalise`). `state()` adds the computed `gate` (what to ask next) and `final` (the G2 AND G4 stickers).
- **Events** gain `actor` and `decision` (`review` per decision, plus `plan_reviewed, stills_reviewed, video_sheet_built, video_sheet_reviewed, video_returned, video_flag, anim_reviewed, pack_final`). `STAGES` grew by those names; `check_animate` accepts any stage from `sliced` on.
- **Files** under `out/G00N/`: `source/plain/S#.png` (the sticker rendered with `outline_px=0` from the very keyed cell, recovery included: the video sheet is built from these), `video_sheet/A<n>/{sheet.png, layout.json, video.<ext>}`.
- **Video sheet (`engine/video_sheet.py`, pure, golden-hash tested).** `build_video_sheet(stickers_rgba, approved, cfg, grid) -> (sheet_rgb, layout)`: a 2048 px canvas of the exact key colour (`#00FF00` or blue), the slots tile the canvas, ONE scale for the whole sheet so the largest subject's longest side is <= 55% of its slot (>= 22% margin per side), premultiplied resize, no outline (it is added once, after the video), rejected slots left pure key colour. `layout.json` = `{canvas, key_rgb, grid, slots[{slot, sticker, rect, subject_rect, scale, subject_px}]}`.
- **Layout slicing.** `process_video(..., layout=, refs=)` decodes each approved slot from the layout's exact rectangles (scaled onto the video), keys every frame with the stills keyer, runs `inside_slot`/`cross_slot` before the encode, then the same normalise / loop close / VP9 encode as before plus `identity_kept` against the approved still. `check_returned_video` runs the `video` stage. The prepared-video sandbox path (`animate`, folder pairing, pre-sliced clips) is unchanged and its results get the same `review`/`history` fields; `edge_touch_frames` stays a warning there.
- **1x1 regeneration** (`POST .../regen {index, subject?}`): a new generation from a prepared 1x1 sheet, `regen_of: "G00N/S#"`, `parent`, the sticker's own key/tags/emoji in the `single_1x1` template, the parent's plan approval inherited; the parent is never modified. 2x2 and 1x1 go through every gate like 3x3.
- **Search** (`GET /api/search?q=`): file search over key, tags, name, task, prompt and emoji, newest first; each row carries its still/animation review state and `final`. Phase 3 swaps Postgres in behind the same route.
