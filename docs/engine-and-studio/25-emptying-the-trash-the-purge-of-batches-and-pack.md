# Emptying the trash: the purge of batches and packs (`flow/purge.py`, 2026-10-03)

<sub>Part of [engine-and-studio.md](../engine-and-studio.md).</sub>

Remove batch, Delete pack and a deleted particle set are soft. What empties the trash is **Settings > Trash** (`console/trash.js`, a card on the Settings screen, no new screen): `GET /api/trash` lists every removed batch and deleted pack with exactly what a purge would remove, Restore sits on each row, *Delete for good* has a plain confirm per item, *Delete all (N)* a typed one (`purge N`, checked again by the server against the trash as it is then). Routes: `docs/api.md` "Trash and purge". Particle sets are not part of the purge yet.

**Delete pack was a hard delete** until this change although the old tracker called it soft (`Library.delete_pack` unlinked the files; the old docs said so honestly). It is soft now: `library.json` carries `trash.packs` (the pack record with `deleted`, `deleted_by`), the stickers and files stay exactly where they were, `Library.restore_pack` brings it back under the same id (so its particle sets still point at it), and `Library._unlink` / `_holders` count trashed packs so deleting a sticker from another pack never takes a file a trashed pack holds. Deleting a single sticker is still immediate.

**What a purge removes, per item.**
* A **batch**: (1) its Postgres rows, `store/purge_rows.py` in one transaction: the `sticker_index` rows **with `subject_vec` / `action_vec`** (so it leaves search), `assets`, `generation_events`, every `stickers` row no `reviews` row points at, every `video_sheets` row no review or task points at, and the `generations` row when nothing points at it any more; (2) a ledger line `begun`; (3) `batches.purge_files`: `out/trash/batches/G###` and `G###.meta.json`; (4) a ledger line `done`. `reviews` are append-only and **stay** (their foreign keys keep the rows they name), so those `stickers` / `generations` rows become **tombstones**, `status = 'PURGED'` (and `still_review` / `anim_review` / `animation_status`), which `pool.reindex` never indexes again; `tasks` (the provider's external task id), `out/jobs/*.json`, `out/tasks/*.json` and `out/model_calls.jsonl` are the spend ledger and stay. Stickers already added to a pack are copies in the library and stay in their packs.
* A **pack**: `Library.purge_pack`: its files under `out/library/files/` (empty batch folders go with them), then its record. **There is no `packs` / pack-sticker table in Postgres** (a pack is library.json; `stickers` / `sticker_index` hold the *batches'* stickers), so a pack purge has no database part, and the "pool copies" of a library sticker are the batch's pool rows, which a pack purge never touches.
* Database absent, `MIRSAL_DB_WRITE=0` or a non-default `out/` (tests, scratch copies): the database step reports `{available: false, reason}` and does nothing; the files are still purged.

**Never silent about sharing.** A pack sticker whose file another pack (live or in the trash) also holds, or a batch whose stickers sit in the shared pool (`sticker_index.shared`, not hidden), is refused `409` in words naming the packs / the pool until the person confirms *that item* (`confirm_shared`). Confirmed, a shared file **stays for the other pack** (deleting it would leave a pack pointing at nothing: no row may point at a missing file), the pack's own record goes, and the pool rows go for a batch. "Delete all" never carries that confirmation; it skips such items and lists them in `refused`. A job in flight for a batch is a `409` in words (like Remove), and so is a running job anywhere (`Console.lock`) or another purge.

**Recorded.** `out/trash/purged.jsonl`, append-only, one line per phase (`kind`, `id`, `phase`, `actor: "human"`, `by`, counts, `confirmed_shared`, `task`), written once per phase so a resumed purge does not duplicate it. It is also what keeps the number taken: `pipeline.purged_ids` is read by `pipeline.next_gid`, so purging the highest batch never lets its number be reused (the database keeps its tombstone and history).

**Long purges.** The route validates, starts **one background thread** (`PurgeTask`, one purge at a time) and waits 1.5 s: a small purge answers `200` with the result, a long one `202` and the caller polls `GET /api/trash/purges/{id}`. The task state is mirrored to `out/trash/purge-state.json`. **Idempotent and resumable:** the last thing to go is what makes the item show up in the list (the trash entry / the pack record), every step tolerates what an earlier run already did (a missing file is fine, a ledger phase is not written twice), and an item that failed stays in the trash with the error in the task (`status: failed`).
