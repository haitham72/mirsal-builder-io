# App design and structure audit — 2026-10-19

Reviewed application revision **`64d8b8a4`**, branch `redesign-ui-ux`. This is a new audit, not a replacement for the historical redesign findings or a claim that those findings were all fixed. No application source was changed.

**Assessment:** the desktop shell, Home and Library have a coherent visual foundation. The largest remaining problems are functional phone editing, keyboard access, finding existing work and maintaining a UI built around shared globals. A new framework or a wholesale visual redesign is not the first step. Fix the reproducible interaction defects, then extract boundaries with contract checks.

- Only G146/G150/G154 artwork folders were copied into temporary output. Two local packs, a 30-message synthetic conversation and deterministic reaction fixtures were constructed there. No real chats, users or jobs were copied.
- All providers and real CLI calls disabled, database writes and tracing off. No paid generation, Telegram send, collection export, deployment or merge. One **Save as new** operation created a row only in the disposable fixture; it is a direct save action, not a confirmation dialog.
- The user's real-data viewer **http://127.0.0.1:8770/** was not automated against or restarted. Audit :8798 is a separate dataset, not the user's app history. The earlier acceptance server :8797 was left alone.
- No page exceptions or HTTP responses ≥400 were observed during the 96-state sweep. This establishes navigation/render health for the sampled data, not end-to-end acceptance of every action. Some state setup used existing controllers directly; targeted follow-up checks used real clicks, hover, Tab and Escape.
- 56 screenshots captured, **14 retained below**. Full numeric evidence and selected accessibility snapshots: [measurements](app-audit-2026-10-19.json). Physical line counts exclude vendor, generated `dist` and Python caches. Coupling counts are static estimates, not runtime performance measurements.

- Not covered: live model quality/latency, LAN guest/staff roles, authentication recovery, actual Telegram/collection delivery, loaded video Prepare editing, every Help/Settings subsection, native screen-reader use, welcome film playback or every route/menu combination. Previous slider/busy/retry and long-chat evidence remains in [acceptance](acceptance-2026-10-19.md); it was not rerun here.
- Existing test results are inherited from the preceding engineering work, **not newly run for this documentation audit**: agent 322 / 4 failures / 9 errors; Node JS 390/390; console wrapper 18/18. Those agent failures/errors still limit release confidence.

## What is working

The four primary destinations are consistent across screens. Desktop Library shows actual packs and separates stickers from reactions. The light and dark palettes retain recognizable selection and focus styling. Reaction styles share state between entry points; their export contracts remain intentionally distinct. Current Emoji-style Motion/Size/Advanced controls and the Lottie player are present. The Lottie editor fits the phone width with an advancing SVG player. The native pack menu fits at 390px; Rename receives input focus and Escape restores focus to its launcher. These existing components should be reused.

The engine/API separation, stable batch/sticker IDs, reversible review decisions, versioned prompts, import duplicate choices and grid mismatch consent are valuable architecture. Keep them through any refactor. New generation defaults are 2×2; explicit and existing 3×3 artwork remains valid. Screenshots of the old 3×3 fixture do not imply a default regression.

### UX-01 — editing and saving on phone

At 390px, `#s-editor .ed-c` and `#s-animate .an-c` both measure **0px wide**. The editor keeps a 220px Layers column and 270px Properties column; Animation keeps 262px and 296px columns. Their root document remains 390px wide while the editor screen internally scrolls to 729px / 606px. The absence of a page scrollbar is therefore not a pass. At 760px the centers are only 222px / 154px; at 1024px they recover to 390px / 322px.

Save sticker has the same family of problem: its `1fr 340px` grid compresses the preview to a stripe and pushes the form beyond the visible right edge. Empty editor/Prepare states fit; the defect concerns populated editing, not all phone screens.

Evidence: [image editor](app-audit-shots/editor-text-390-light.jpg), [animation editor](app-audit-shots/animate-390-light.jpg), [save form](app-audit-shots/save-sticker-390-light.jpg). Source: `console/studio.css:38,81–87,104,137`; `console/editor.js:97,205–209`; `console/animate.js:8`.

Propose: one visible primary workspace on phone, with Layers/Properties as accessible panels; stack preview/form on Save. Preserve all tools, text layers, trim/frame controls, Resize semantics and unsaved edits. Acceptance: actual canvas and Save action reachable at 390/760/1024/1440, both themes, with keyboard and zoom; assert panel bounds, not merely document width. No framework migration is needed for this fix.

### UX-02 — dark primary hover

On Home's Start creating button, stable computed colors are `#071015` on `#22d3ee` normally (**10.62:1**), then `#071015` on `#20262f` on hover (**1.26:1**). `theme.css:31` overrides the lower-specificity `.btn.pri:hover` background while retaining primary text color. This is separate from the selected-tab hover fixed earlier.

Evidence: [hover failure](app-audit-shots/home-primary-hover-1440-dark.jpg), [normal desktop](app-audit-shots/home-1440-dark.jpg). Fix the shared primary state once and verify representative Home, dialog, Studio and export buttons, including disabled/focus states. Ordinary text needs 4.5:1 under [WCAG contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum); hover text is included.

### UX-03 — mouse-only sticker actions

Pack `.cell` is a clickable `div` with no role and `tabIndex=-1`; `.selbox` is a clickable span. Preview/Edit/Timeline/Cover/Delete live in `.hov`, which is `display:none` until `.cell:hover`. In an actual Tab walk from Open in Studio, focus skips all nine sticker tiles and all their actions, reaches reaction controls, then leaves the content. A CSS focus ring alone cannot make those tiles keyboard reachable.

Evidence: [pack grid](app-audit-shots/pack-1440-dark.jpg), measurement `keyboard.packTabStops`. Source: `console/packs.js:28–31`, `console/studio.css:70,263`. Give each sticker a named native opening control and an operable selection control; reveal secondary actions on `focus-within` as well as hover. Avoid nesting buttons inside a button. Retain pointer drag/marquee and multi-select. Acceptance: Tab/Enter/Space can view, select, edit and reach Timeline without a mouse. See [WCAG keyboard guidance](https://www.w3.org/WAI/WCAG22/Understanding/keyboard).

The preset preview stage is also a clickable div (`reactions.js:103`); inspect its explicit Open action when fixing the pattern. Emoji bank buttons already provide an alternative route, so this audit does not claim all reaction editing is keyboard blocked.

### UX-04 — editor control labels

The browser accessibility tree exposes unnamed Scale/Rotate sliders and number inputs, font/zoom selectors, text and color fields. Nearby visible text is not programmatically associated with these controls. Source: `console/editor.js`, `drawProps`, `transform`, `textCtl`. The geometry defect must not hide this separate issue. Acceptance: each control has a stable descriptive accessible name and linked units; text styles exposed as controls rather than unexplained “B I”. Use labels/IDs or explicit names without changing payloads.

### UX-05 — frame preview keyboard behavior

Opening the real G146 frame test card leaves focus on `body`; Escape leaves `#vzcard` open. Apply/Cancel exist and Cancel works by click. `ui-testcard.js:5–13` adds a `role=dialog` element to the body without entry focus or dismissal handling. The ordinary Rename dialog already demonstrates focus entry and restoration.

This test card is **non-modal**: do not impose a modal focus trap or claim that lack of containment itself violates a modal contract. Add intentional entry focus, an Escape-to-Cancel path and return to the launcher, preserving staged values and zero mutation on Cancel. Confirm whether the edge card should share the same policy. Evidence: measurement `keyboard.frame`; compare [modal focus guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) only for actual modal dialogs.

### UX-06 — workspace identity and apparent data loss

The copied-data server has the same app title, shell and empty-state language as the real-data server. The user's earlier “everything is empty” report followed opening the acceptance dataset. The data was intact on :8770. Nothing in the Home UI makes that distinction apparent.

Evidence: [Home](app-audit-shots/home-1440-dark.jpg), `HANDOFF.md` viewing correction. Propose a compact **Test workspace** identity on task/test servers, or a named local workspace switch/status, with counts and recovery links in empty states. A raw filesystem path need not appear throughout the product. Decide the workspace identity contract in the API before adding UI-only detection based on a port number.

### UX-07 — current work and recovery hierarchy

In the sampled reopened Studio state, an expanded New request composer and Edge section sit above the selected batch; its actual artwork begins near/below the desktop fold. This is not a fresh-session test of disclosure defaults. At 390px, the batch header/toolbars plus the sticky Add to pack card dominate the first viewport. Existing work is available in the secondary list but that list is behind a generic Lists button on phone.

Evidence: [desktop Studio](app-audit-shots/studio-stills-1440-dark.jpg), [phone Studio](app-audit-shots/studio-stills-390-light.jpg). This is an information hierarchy recommendation, not a broken route. Propose keeping selected work prominent, compacting the new-request block for reopened batches and naming the recovery entry for batches/conversations. Measure clicks to resume real work, not only clicks to create.

**Preserve the owner's choice:** Create starts a fresh Chat/Studio. Do not silently change that behavior to resume the last project. Improve the explicit recovery path instead.

## Folder, file and naming audit

The nested `mirsal/mirsal` path is normal project/package separation, not a naming defect. Keep the useful `engine`, `agent`, `flow`, `generation`, `media`, `runtime`, `services`, `store` and `vision` domains. Do not turn `services` or `utils` into catch-all folders.

### AR-01 — API boundaries

`console` currently contains **7 Python files, 40 first-party JS files and 3 CSS files**, together with UI assets. `server.py` is 2,392 physical lines; `app.py` 1,268. AST spans: `make_handler` 1,686 lines, nested `_post` 514, `_get` 325; `create_app` 1,092. These spans overlap by nesting, so they must not be added together. Transport, compatibility dispatch and UI serving are hard to review independently.

Extract native domain routers from `create_app`, schemas from `app_models.py`, and explicit dependencies from the adapter. Keep the legacy transport isolated until parity is demonstrated. The [FastAPI APIRouter pattern](https://fastapi.tiangolo.com/tutorial/bigger-applications/) is a suitable convention, not a mandate to move every endpoint at once.

### AR-02 — feature boundaries before file moves

The AST scan finds **928 top-level names**, **514 action names / 515 definitions**, and 17 renderer names / 22 assignments. There are no duplicate top-level declarations; `ggo` is the deliberate action replacement, and several renderer assignments are extension hooks. Do not treat those counts as 514 dead actions or automatically remove hooks.

The approximate call scan yields **561 candidate cross-file edges** and a **19-file mutually connected group** spanning shell, Library, packs, Studio, editor, Chat and Reactions. This scan matches unqualified calls to top-level names without full lexical resolution: local shadowing can overcount; member/dynamic calls are omitted. It is evidence for investigation, not a precise import graph or proof of runtime circular-import errors.

Concrete coupling: `particles.js:193–197` renders private Emoji/Lottie views for Library; `reactions.js` renders the Packs presenter; `particles.js:131–134` wraps and replaces `stepsHtml`. `app.js` owns navigation and dispatch while feature scripts mutate shared state. This makes route transitions, stale async responses and script order part of each feature's implicit contract.

Extract shared Reactions views with explicit context, then route controllers with enter/leave/dispose and request ownership. Consolidate existing slider/download/preview/cache tasks **T-024/025/031/034/035** rather than duplicating them; watcher/edge synchronization is a separate remaining extraction. Keep `ACT` compatibility until the baseline inventory and click contracts are preserved. A file move without state ownership will not resolve this.

### AR-03 — CSS and template maintenance

First-party console JS is **800,448 bytes**, CSS **230,267 bytes** (source sizes, not transfer/performance budgets). JS has 277 physical lines longer than 300 characters and 294 textual inline-style occurrences; CSS has 68 long lines, 753 hex-color occurrences and 11 `!important` occurrences. Hex matches include legitimate media/background colors; these are not 753 violations or distinct colors.

`studio.css` alone is 175,945 bytes across 1,235 lines. `particles.js` is 74,846 bytes despite only 506 lines. The measured hover regression shows the practical consequence of overlapping control rules. Extract base controls/states, tokens and feature styles; keep intentional checkerboard/media colors. Reflow touched templates so controls can be reviewed. Do not create one new global stylesheet per tiny component.

**Already shared:** `TESTCARD` exists; ordinary dialogs have focus management; `RX`/`LS` slider rendering already has reusable patterns. Do not propose extracting a second copy of these helpers. Their remaining policy gaps are UX-04/05 and AR-02.

### AR-04 / AR-05 — orchestration and runtime boundaries

- `agent/graph.py` 2,667 lines; `generation/actions.py` 2,276; `flow/particle_sets.py` 1,819; `flow/pipeline.py` 1,575. These merit responsibility-level extractions: checkpoint/replay lifecycle, graph construction/nodes, provider job lifecycle and particle ownership/render/save lifecycle. File size alone is not proof that splitting improves behavior. Preserve the newly fixed replay/spend boundary and cancellation ordering.
- Ten first-party `setInterval` sites exist, plus timeout-based polling. Several already guard route/visibility or job state. This audit does **not** claim all polling leaks. Give watchers one lifecycle owner, then verify off-route cancellation and request counts; reuse earlier overlap evidence.
- **3,477 tracked files under `mirsal/out/`**, plus reference/artwork/workbench material at the root, blur source and local output. SQLite files remain ignored. W29 already asks whether to untrack runtime data and requires a backup/retention decision. Do not delete data, rewrite history or stage runtime output as part of this audit. W33 separately owns deletion of the 36 tracked parked `mirsal/web/` files. Existing `console/dist` is not the active first-party UI and is excluded from measurements.
- Keep the source photo `Custom_emojis/Original_emojis/rashed 02.jpg` as previously decided. A future reference-assets move can improve provenance without re-encoding media or rewriting history. Grouping root artwork should follow the runtime/source decision, not lead it.

### Proposed structure and naming

This is a migration target, **not an implemented tree**:

```text
mirsal/                         project configuration, tests and package
  mirsal/
    api/
      app.py                    app construction / middleware
      dependencies.py           shared request context / guards
      routers/                  chat.py, generations.py, imports.py,
                                reactions.py, packs.py, settings.py
      schemas/                  domain request/response schemas
      legacy_adapter.py         existing compatibility boundary
    console/
      ui/
        shell/                  navigation, dispatch compatibility
        features/               studio/, chat/, library/, reactions/, editor/
        shared/                 dialog, controls, preview, request lifecycle
        styles/                 tokens, base, feature styles
        assets/                 existing UI artwork and fonts
        vendor/                 pinned third-party browser runtime
    agent/                      lifecycle + graph + intent/node modules
    engine/ flow/ generation/ media/ runtime/ services/ store/ vision/
```

Use **`api/routers/` for HTTP endpoints**, **navigation/router** for browser hash dispatch, and **intent routing** for the agent. Use **schemas** for HTTP shapes, domain models for application records and provider/client names for external integrations. Python module names should be lowercase with useful underscores, per [PEP 8](https://peps.python.org/pep-0008/#package-and-module-names). `observability` and `telegram_chat.py` are clearer expansion candidates for `obs` / `tg_chat.py`, but their renaming has lower payoff than the boundaries above.

Avoid creating another ambiguous top-level `web/` alongside the parked React tree. The proposed `console/ui` is the current sandbox's home. ES modules or another loading mechanism can follow explicit dependencies; a new bundler/framework is a separate decision. When moving assets, update `UI_FILES`, script order, serving paths and inventory together. Keep public route names, IDs, stored paths and JSON payloads compatible.
