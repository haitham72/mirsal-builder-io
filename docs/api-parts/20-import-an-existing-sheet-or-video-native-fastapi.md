# Import an existing sheet or video (native FastAPI)

<sub>Part of [api.md](../api.md).</sub>

The Studio offers **Use my own sheet** and **Import from Higgsfield** to the owner. These routes never generate or spend credits and also have `/api/v1/` aliases.

- `POST /api/import`: raw bytes, query `name`, optional `prompt`, `generation`, `sheet`, `retry`, `job` (a failed local job this file completes), `as_new` (an unrelated batch even when a failed job matches), `batch` (any `G###` of a batch: import INSIDE it, see below). PNG/JPEG/WebP images become batches; an MP4/MOV/WebM video with `generation` or `sheet` goes to that destination's G3-approved video sheet (first approved sheet if `sheet` is omitted); a video with neither is a batch of its own (`flow/imports.py` `first_frame`: its first frame, `<file>-frame0.png`, is the sheet the stills are cut from, the video is its prepared 3x3 video, and the stills and the animations are cut in one go, then wait for review; the answer is `{id, kind: "video", import, subject}` without `sheet`). A file naming a provider ticket with exactly one matching failed job completes it (`recovered_by: "manual import"`, no second charge: a sheet job's batch is built from the job's own saved plan and carries its external task id, a video job attaches to the job's own batch and sheet); several matches are a 409 with `candidates`. Both local and remote uploads use the existing 300 MiB video-upload cap.
  With `batch`: a picture is that batch's next generation (its plan and naming, `parent` + `regen_of`, like Regenerate), a video attaches to the batch's main generation and the sheet it was animated from is read from its first frame (image sheet -> the generation's 3x3 video, re-animating the kept stickers; a video sheet -> its next animation). 202 `{id, kind, import, batch, main, generation, sheet?, match?: {sheet, distance, distances}, message}`; the same bytes again are a 200 duplicate; 409 while the batch's stickers are not cut or a video is being cut.
- `GET /api/imports/candidates?ticket=`: the person's own FAILED/TIMEOUT jobs holding that ticket, newest first — the import dialog's "Is this the result of …?" (prompt, time, thumbnail; a sheet job has no picture yet, so the dialog shows the file being imported).
- `GET /api/higgsfield/history?size=40`: image/video jobs, newest first; size 1–100; each has a `known` location when already present.
- `POST /api/higgsfield/import`: JSON `{id, prompt?, generation?, sheet?, retry?, local_job?, batch?}`. Downloads only a completed HTTPS result, with bounded reads and the project's TLS context; validates a video's destination before downloading when one is named (none: the video becomes a batch of its own, as above) (`local_job` completes that failed local job instead of starting an unrelated batch).

Accepted imports return 202 `{id, kind, import, subject? or sheet?}`. Duplicates return 200 `{duplicate: true, by, job?, task?, generation?, effect?, import?, status?, recoverable?}`. IDs are checked against jobs, task reservations and successful download logs; bytes against download hashes and the import ledger. A failed job without a generation does not prevent importing a result recovered manually. A pending job/task remains addressable as existing work. An import interrupted in processing can be explicitly retried into its saved batch; a ledger reservation made before batch allocation is recovered by source path. The background worker preserves the actor and records READY/FAILED in `out/imports.jsonl`. The server's existing writer lock and the serialized import allocation prevent concurrent duplicate batches; media names and ledger IDs use UUIDs. Errors retain `{error}` with 400/409/413/502/503 as appropriate.
