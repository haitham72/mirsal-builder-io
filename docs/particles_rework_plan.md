# Particles rework plan (Haitham, 2026-10-03): particles live in the sticker, not in a pack

**Status: ownership, scope, galleries and chat are implemented in the working tree; compact UI, animated sprites and recovery acceptance remain in progress (2026-10-04).** Written for the LLM session that implements it. It supersedes the "a set belongs to pack(s), not to stickers" decision of `docs/particles_plan.md` §1-§2 (Haitham reversed it, see item D below); The area documents now describe sticker ownership. The latest full-flow correction is `sticker_particles_flow.md`. Read first: `CLAUDE.md` (rules 6, 10, 11, 12, 13), `docs/particles_plan.md`, `docs/effects.md`, `docs/design.md` §9-§10, `docs/waiting-for-haitham.md` items 24-28, then the code map in §1 below. Line numbers drift (the tree is edited constantly): find things by name.

## 0. What Haitham reported (his words, numbered; the plan answers each)

1. New stickers that were not created as a pack: clicking *Generate particles* never shows them. Wanted: ask **"approve as a pack before generating particles for it"**. When *Generate particles* is clicked it must open **already scoped to that batch**, not show overall stickers at random.
2. The selection for particles is confusing. *Create with AI* should have **two options**: (1) generate a sticker sheet, (2) create a video **from scratch** (from nothing to nothing); **both must be usable in simulation**. *Create from sprites*: select **slices as sprites** in the simulation.
3. "Use this particles with which pack?" is **untestable**; it should be testable in the **chat**; when the user says they like it back, the chat prioritises the **assigned** particles first.
4. Particles **never live in their own pack**; they always live **inside the sticker that created them**. Adding to a pack only **affirms** it in the *Particles — What was made for each sticker of this batch that is in a pack. Saved results show here.* section.
5. Clicking *Create particles for pack* again should **create more, seamlessly, and more and more, in the same pack**.
6. Even when the user created particles for a pack, it is still registered as **"never created"**.
7. There is still **no trace of "particles created via Kling"**; either the same sprites or generated images; both are fine.
8. Clicking *add particles* on a new or old stickers pack **opened the previously created particles set**, a very strange UI/UX interaction.

## 1. What exists today (verified by a read-only code map, 2026-10-03)

- **Two entry screens, two state objects, shared functions in `console/effects.js`:** the Studio *Particles* tab (`console/particles.js`, state `SP`, the wizard `spView/spBody/spSetupHtml`, cards `SPKINDS` = *Pack stickers* / *Drawn particles* / *Use an existing set*) and *Create > Particle effects* (`#/effects`, `effects.js` `fxSetup`, state `FX`, radio *Simulate* / *Video from scratch*). The video kind is coded in the Studio tab (`spKind`) but hidden (no `SPKINDS` card; the localStorage restore accepts only `pack|drawn|existing`).
- **Data model:** a set `P###` (`flow/particle_sets.py`, `out/particles/P###/set.json`) with `source{kind drawn|stickers|video, effect, generation, ...}`, `cells[]`, `motion`, `renders[]`, and **`packs[]`: the only link** (`assign/unassign`); there is no per-sticker link. The older working run `E###` (`flow/effects.py`) is per pack and per stickers; `source={"effect","result","source_sticker","source_pack"}` is stamped on stickers made from it.
- **The batch's *Particles* section** (`spSecHtml`, `spSecBatchHtml`, `spSecData`, `spLinkIndex` in `particles.js`) draws three groups from the legacy E### model: `got` (a linked pack sticker with particles), `none` (linked, none yet: chips `spmake`), `free` (a batch cell **not in any pack**: only thumbnails and the text *Add to a pack to give them particles*, **no button**). A cell is "linked" only when a library sticker has `source.generation == G###` and `source.index == cell`. Counts come from `GET /api/packs/{id}/particles` -> `counts_for_pack` (`flow/effects.py` `_gallery`), which **ignores P### sets, their renders and the chat's sets entirely** (that is the cause of item 6).
- **`ACT.spopen`** only calls `spShowTab`; `SP.eid` is persisted in localStorage `mirsal.sp`, so the **old run reopens** (item 8). `spDefaultPack` chooses the pack with most of the batch's stickers, else `SES.pack`, else **the first pack that has any stickers**, and `spPickSel` ticks that pack's first 24 stickers (`SPMAX=24`): a batch in no pack gets someone else's pack (item 1). `ACT.psmakepack` (pack page) clears `SP.eid` (fresh run each click); *Use as particle set* always makes a **new** `P###` (no reuse), `spmake`/`spOpenFor` reset the run; only *Generate more* (`POST /api/particles/{id}/more`) appends cells to the same set (item 5).
- **Kling video:** only on `#/effects` ("Video from scratch": `POST /api/effects/{id}/estimate|video`, 409 until `go:true`; prompt in `generation/effect_prompts.py`, cut/repair in `engine/effect_video.py`, checks `engine/effect_checks.py`). Its clips become ordinary animated stickers via `/api/effects/{id}/add`; the Kling mode is only discoverable by looking up the E### result. `particle_sets.KINDS` contains `video` and `set_from_effect` would set it, but `fxBody` offers *Use as particle set* only when `sim`, and a video effect has no `set.generation`, so **a Kling take can never become a set** (item 7). The legacy card labels it "video, cell N · shared by its group" (`packs.js` `ptCard`).
- **Chat:** `agent/resolver.py` `particles_intent` (`make|more|delete|restore|assign`), `agent/graph.py` `_particles_make` (pack by `_named`, else the only pack, else "Which pack?" chips), `_focus_set` (named set, else `sess["particles"]["set"]`, else the only set), `tools.particles_start` always **creates a new set** on the pack; **no "assigned set first" logic exists anywhere**. The old `EFFECTS` intent (`n_effects`, `tools.effects_start`) opens an E### in video mode.
- **"Use this particles with which pack?" does not exist as a string.** The closest texts: wizard *Which set goes on {pack}* (`particles.js:41`), *Use as particle set* dialog with field *Where does it live* and *Tick packs, or nothing for a stand-alone set* (`effects.js` ~267), the Assign dialog (`particles.js` ~169), the pack page's *Use an existing set* dialog (~323). Under the new model these questions disappear (see D).

## 2. The target model (decisions this plan makes; Haitham may veto in review)

**D. A particle set is owned by stickers (library stickers that came from a batch cell), never by a pack.**
- `set.owner` = the library sticker id(s) it was made for (`stickers[]` of `{sticker_id, pack_id (derived), generation, index}`; `source.generation/index` stay as provenance). A set has **no `packs[]` and no pack-level standalone state**; the pack page shows the **union of the sets of its stickers**. Migration: for every existing `P###` with `packs[]`, set `owner` = the stickers of those packs that appear in `source.sticker_ids`/the effect's stickers; a set with no derivable owner stays **detached** and is shown in the Library > Particles tab with one action, *Attach to a sticker* (nothing is deleted; rule 7 of the particles plan: restore stays).
- **Affirm:** a set is *made* on the sticker the moment it exists; **adding its burst to the pack** (`POST /api/particles/{id}/add`) **affirms** it: the sticker's row in the batch's *Particles* section turns from "made" to "in the pack ✓". There is no separate "assign the set to a pack" step and no per-pack set.
- **Many sets per sticker, accumulating:** a sticker has an ordered list of sets (`sticker.particles = [P###...]`, newest last). *Create particles* on a sticker that already has a set **adds cells to its newest set (Generate more)** unless the person chooses "a fresh set" (a small secondary link). (Item 5.)

**E. The batch is approved as a pack before particles are generated (item 1), and it is an offer, never a wall (CLAUDE.md rule 10, "never a block a person cannot get past").** The *Particles* section for a batch with stickers not in a pack shows, per such sticker or once for the batch, a compact **"Approve as a pack"** offer that opens the existing Pack modal (`ACT.gadd`, `pwSync`, `ACT.pwgo`) and, when it finishes, **returns to the particles wizard scoped to the batch and continues** (no second click to find it again). Nothing else is offered for a not-in-pack sticker; the old dead-end line *Add to a pack to give them particles* is removed.

**F. *Generate particles* always opens scoped (items 1, 8):** the entry carries `{generation, sticker_index | sticker_id}` (from the batch section chip, the batch header button, the pack page, the sticker carousel). The wizard **starts fresh for that scope** (never the persisted `mirsal.sp` run unless the person clicks *Continue the last run* shown only when it matches the same scope). The default-pack guessing (`spDefaultPack`, "first pack that has any stickers", "first 24 stickers") is deleted: no scope, no wizard body; a scope-less entry (the Library tab's *Make particles*) first asks **"Particles for which sticker?"** with a picker of batches/packs and then enters the scoped flow. A batch's stickers are the preselection; other stickers are never ticked.

## 3. The creation choices, rebuilt (item 2)

Exactly **two top-level cards** (the third, *Use an existing set*, becomes "Reuse particles of another sticker", see §6):

1. **Create with AI** (costs credits, price on its own line first, rule 13). Inside it **two sub-options, both feeding the same simulation**:
   - **Sticker sheet** (today's *Drawn particles*: a 2x2/3x3 sheet drawn through the sheet pipeline, cut into cells; `pipeline` kind `particles`, `recut_as_particles`).
   - **Video from scratch** ("nothing to nothing": text-only Kling clip that starts and ends empty, `effect_video` template, `estimate`/`video` routes, the empty start/end checks, 2x2 default, 3x3 flagged measured-poor). **Required:** its cut cell clips are saved as animated sprites, with temporal RGBA frames playing inside the simulation. Peak PNGs are posters/fallbacks, not the animated simulation input, and the set records `source.kind="video"` with the job id. This implements the dead `kind: video` path of `set_from_effect`: copy the cut clips into `set.cells[]`, set `w/h/key/sprite`, status from `effect_checks` (warnings only; rule 10).
2. **Create from sprites** (free): the person **selects slices as sprites**: slices of the batch's sheet (the clickable cells of the left image sheet, the same hit areas as the allow/drop cells) and/or the batch's stickers; the chosen cells become the set's cells (`source.kind="stickers"`, `sticker_ids`/`slices`), and the simulation runs on them. No per-pack stickers list, no `SPMAX` default fill.

Both cards end in the **same simulation block** (`fxMotion`/`spBurstHtml`: presets Energy/Float/Swirl... sliders, live preview, Render, *Add to the pack* = affirm). The Kling path is therefore **simulatable**; it also keeps its own "use the clip as the sticker" route (`/api/effects/{id}/add`) as a secondary link inside *Video from scratch* because that exists and works.

**Trace of Kling (item 7):** every set shows its `source.kind` as a plain chip on its card and in the batch section (*From AI sheet* / *From Kling video* / *From sprites*), with the job id and credits; stickers added from a burst carry `source.particle_set`, `source.kind`, and the render id. The legacy card label stays.

## 4. The batch section and the counts (items 4, 6)

- *(Superseded 2026-10-04: the batch section is one list of versions, each once, not a block per sticker; `docs/particles_plan.md` §5.)* `spSecData` / `spSecBatchHtml` are re-pointed to **sets by owner sticker**: for each READY batch cell, the row shows the sticker's sets (kind chip, cell count, thumbnails), `made` vs `in the pack ✓` (affirmed), buttons *Create particles* (scoped), *Generate more*, *Open*. A cell not in a pack shows the Approve-as-a-pack offer (E). Retire the legacy `ptBadge` double-count or merge it (waiting-for-haitham item 28).
- The section text changes to say what is now true: **"Particles — made for each sticker of this batch. Adding a burst to the pack affirms it."** (`tests/test_js.py` and `tests/js/particles.test.js` assert the old sentence: update them with the change.)
- Members get the same read data they get today (owner-only writes stay).

## 5. *Create particles for pack* again = more of the same (items 5, 8)

- The pack page button and the section chips call the scoped entry; for a sticker with a set it opens the **set's "Generate more"** (all creation choices available regardless of `source.kind`, price shown first) and appends cells to that set; the person never sees a new empty wizard unless they ask for *a fresh set*.
- The pack-level entry (*Make particles for this pack*) means "for these stickers": it opens the scoped picker with the pack's stickers listed, **those without a set first**, one run per ticked sticker group (a run creates one set for a group of stickers that share it: decide in §6).
- `SP.eid`/`mirsal.sp` persistence is reduced to *Continue the last run* for the same scope only. Opening a set is an explicit *Open* on a card, never a side effect of "add particles".

## 6. Reusing a set on other stickers; the chat (item 3)

- *Use an existing set* becomes **"Use the particles of another sticker"**: pick a sticker (or several) that already has particles, copy the **link** (`sticker.particles += P###`, the set's `owner` gains the sticker; the set is unchanged and never copied unless *Duplicate*). No pack question anywhere. This also removes the untestable "with which pack?" dialog.
- **Chat:** the particles intent works on **stickers/batches/packs by what they hold**: "make particles for the Princess pack" asks for nothing more than the pack's stickers (offers the Approve-as-a-pack card first when a batch has none); "more particles" targets the **focused sticker's newest set**; "use them for the next one" is a link edit. **Selection order:** an explicitly named set overrides; otherwise use the sticker's newest owned set, then the focused set, then the only suitable set, else chips. Render and *Add to pack* use the same order. Write this order once in `agent/graph.py` (`_focus_set`) and use it everywhere; document it in `docs/agent-and-chat.md` ("Particle sets in the chat"). Tests drive the chat: a sticker with two sets, "burst for sticker 3" picks its newest owned set without asking; a message naming another set overrides it; none owned asks with chips; the Approve-as-a-pack card appears for a not-in-pack batch. This is how "which pack?" becomes **testable in the chat** instead of a modal.
- **Echo interpretation settled by Haitham, 2026-10-04:** assignment tests saved particle settings in **Mirsal Echo**. Save the set's motion, branch with Save as new, assign that branch to another sticker, and Test in chat. Echo's actual reply/reaction on the sent sticker plays that sticker's newest assigned set with its saved settings; the preview overlays the outgoing sticker. Reaction replay resolves its current assignment again. No assignment means no particle preview, never a focused/session-set fallback. The endpoint is `GET /api/packs/{pack}/stickers/{sid}/particle-preview`; it is free and does not require Render/Add. Natural-language AI-chat set resolution remains the separate selection rule above.

## 7. API (engine function + stable JSON first, rule 11)

Additive wherever possible; nothing existing changes shape without an entry in `docs/api.md` and `console/openapi.py` (the drift test guards it).

- `GET /api/particles` / `GET /api/particles/{id}`: add `owner[]`, `kind` chip data (`source.kind`, `job`, `credits`), `affirmed_in[]` (pack ids where an owner sticker has a rendered burst added); keep `packs[]` as a **derived, read-only** list for compatibility.
- `GET /api/stickers/{pid}/{sid}/particles` or extend `GET /api/packs/{id}/stickers/{sid}/particles` (`for_sticker`) to return the sticker's sets (P###), not only E### results; `GET /api/packs/{id}/particles` returns the union of its stickers' sets plus the legacy counts, with `counts` summing both.
- `GET /api/generations/{id}/particles`: the batch section's one read (per cell: linked sticker or `null` + the offer flag, sets, affirmation).
- `POST /api/particles {from_effect|from_generation|from_slices|from_video}` gains `owners:[{pack_id, sticker_id}]` instead of `packs`; `from_video` implements the Kling set (copies cut clips, `source.kind="video"`). Unknown `packs` in old clients are mapped to the pack's stickers for one release (deprecated, documented).
- `POST /api/particles/{id}/more` unchanged (appends); `POST /api/particles/{id}/link {sticker_ids}` and `/unlink` replace `assign/unassign` (keep the old routes as aliases that map a pack to its stickers); `POST /api/particles/{id}/add {renders, pack_id}` keeps its contract and now also writes the affirmation (`render.affirmed_in += pack_id`).
- Chat tools (`agent/tools.py`): `particles_start` takes the owner stickers (not a bare pack) and reuses/extends the sticker's newest set unless "a fresh set"; add `particles_link`; `effects_start` (the old Kling-only intent) is folded into the new Kling sub-option (the card links to the scoped wizard, not `#/effects/E###`).

## 10. Rules to keep (do not break while doing this)

- **Never a block a person cannot get past (rule 10):** the Approve-as-a-pack step is an offer with a one-click path; effect checks stay warnings with "use it anyway"; only Telegram's own limits stop anything.
- **No spend without the price first (rule 13):** AI sheet and Kling always show the price on its own line and spend on that click only; tests use fakes (`MIRSAL_NO_REAL_CLI`).
- **Engine function + JSON contract first (rule 11); no dead stubs (rule 6):** every control above has its route; the old routes stay as documented aliases for one release.
- **Soft deletes stay soft:** a set deleted from a sticker goes to the particle trash (restore works) and the purge (`flow/purge.py`) learns the new owner links (a purge of a sticker's pack must not orphan a set silently: the set is detached, listed, never deleted by a pack purge).
- **FastAPI/pydantic follows completed particles acceptance, as authorized 2026-10-04** (`docs/fastapi_plan.md`), do not rename watch folders, do not commit tokens, never `git add -A`.

## Implementation decisions (2026-10-03)

**2026-10-04 correction from Haitham:** simplify the entire visible flow (`sticker_particles_flow.md`) and restore **prompt → Kling 2×2/3×3 animated sheet → slice → animated sprites in the particle simulator → add to the same pack**. Each sprite retains its temporal animation inside the simulator. The peak-frame decision below is superseded as simulation input: PNGs remain posters/fallbacks, and animated clips supply frame sequences. Video generation must stay available in Add more regardless of the set’s initial source. The complete video acceptance is outstanding; a finished fixture injected into a Render panel is insufficient evidence.

§11 settled: owners are library stickers; a selected group may share a set; Kling keeps animated cell clips for temporal simulation and tight keyed peak-frame PNG posters. Haitham clarified assignment's purpose: testing saved settings in Mirsal Echo, where the actual sent sticker's reply/reaction uses its newest assigned set and saved motion. Branching then assigning to another sticker makes that branch independently testable. Echo has no unrelated fallback. Separately, AI-chat natural-language requests prefer the focused sticker's newest set, with an explicit named-set override. The legacy badge sums owner sets and legacy results. Adding the burst as an ordinary animated sticker affirms it; separate Telegram effects/download delivery and per-emoji motion remain open.

Phase 1: owner records, idempotent backup migration, derived compatibility packs, link/unlink aliases, batch/sticker reads, summed counts, slice import and Kling peak sprites are implemented. Purging a pack detaches sets rather than deleting them. Implementation tests used scratch data; no implementation test may migrate the real out.

Phase 2: all entries carry explicit scope; library entry asks for a sticker; old-run continuation requires a matching scope. Pack approval returns automatically to that batch.

Creation flow (phase 3): the scoped two-card UI and import paths are implemented, but its previous browser fixture only checked the static panel. The full animated-sprite pipeline and compact Add more source selection remain under acceptance; do not count this phase complete until they pass.

Phase 4: the batch section reads `/api/generations/{id}/particles` and shows each sticker’s own sets, source, job, credits and affirmation. Pack cards show the union of their stickers’ sets; a sticker’s view filters that union by owner. The badge sums sets, legacy results and saved stickers once. Detached sets offer attachment to stickers, and link edits never ask which pack owns the set.

Latest acceptance direction (2026-10-04): prioritize already-created sheets/clips copied to scratch out. Trace their actual effect/job/generation paths and recorded state, explain why a run is stuck, and recover with free recut/import/recovery through temporal simulation, Render and Add. Do not launch fresh generation merely to satisfy acceptance. Synthetic temporal tests supplement recorded-artifact recovery; neither a new provider call nor an injected finished Render panel replaces it. Record diagnosed causes and available recovery in the area docs, then remove this completed checklist only after the coordinator confirms all particle gates.
