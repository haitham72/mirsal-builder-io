# The vision judge (`mirsal/vision/`)

<sub>Part of [agent-and-chat.md](../agent-and-chat.md).</sub>

A pre-reviewer, never the gate. `python -m mirsal judge G002 [--anim] [--force]` (or `POST /api/generations/{id}/judge`): each READY sticker is shown on a grey
background with what it was meant to be (the first approved sticker is the reference); the answer is JSON `{decision, confidence, scores, reasons[], suggested_emoji,
notes}` with reasons from a fixed list (DUPLICATE, WEAK_CONCEPT, AMBIGUOUS_ACTION, STYLE_DRIFT, IDENTITY_DRIFT, SEVERE_ARTIFACT, POOR_COMPOSITION, ANIMATION_RISK,
CHROMA_RISK, MISSING_REQUIRED_ELEMENT, ANATOMY_ERROR, OBJECT_DEFORMATION, EMOJI_MISMATCH, UNWANTED_TEXT). An animation is judged as four frames side by side.
The verdict is a history line with `actor = 'vlm'` at the same gate (it shows in the sticker detail) and `sticker.judge`; it never changes `review.*`. The answer is
parsed tolerantly, validated, repaired once, and on failure the sticker is **unjudged** (`FAIL_CLOSED`, the default; `DETERMINISTIC_ONLY` says nothing). Verdicts are cached in
Redis by image hash + model + judge version + context; calls are limited by `VISION_CONCURRENCY` (2). `recovery.plan_recovery` turns the rejections into a
**recommendation** (regenerate 1-2 cells as 1x1, or a new sheet after more than 2 rejected, at most 3 sheets and 2 attempts per cell; one sheet with the other key colour
on a colour problem) and spends nothing. **Uncalibrated** until Haitham labels 30 stickers (`docs/measurements.md`, W11). There is no `vision/calibrate.py` or `mirsal judge calibrate` command in the current build; do not present the report's suggested command as runnable. Labels and agreement measurement remain an operator task, not a correctness defect in pre-review.

**Consent.** Sending a picture to a vision model is the one thing that moves image content to a model (LM Studio locally, OpenAI when the vision provider is the cloud), so it needs the person's yes, asked **once** ("Allow AI vision of generated media?"), never per run. The rule lives where the model would be called (`vision/consent.py`: `require(allowed)`, `allowed` must be exactly `True`), not in a screen: `judge_generation` and `transcribe.captions_for` raise `ConsentRequired` before any image is read for a model, and the HTTP routes turn it into `409 {error, consent_required: true}` (`POST /api/generations/{id}/judge` and `.../captions` need `allow_vlm: true` in the body). The operator's CLI (`mirsal judge`) is an explicit command and passes it. In the chat the answer is `settings.allow_vlm` (`None` = not asked, `True`, `False`), changed by the single AI vision switch under the first answer (a settings-only press, which flips on a second press), by the pending "Allow AI vision / Not now" pair of a describe or names request, or by typing "allow AI vision" / "don't use AI vision"; the Studio keeps it in `localStorage` `mirsal.allow_vlm`.

**Per-frame captions** (`vision/transcribe.py`). `captions_for(out, gid, force=False, allowed=None)` returns one `FrameCaption {generation_id, index, row, col, grid, png, caption, text_visible, verdict, reasons, model, cached, error}` per READY sticker, the grid read from `result.json` (2x2 and 3x3 share one path); the verdict is the judge's, already on the sticker, so a caption costs one model call per cell and none for the verdict. It goes through the judge's own logged, parsed, once-repaired, cached call (`VLM_CAPTION` in `out/model_calls.jsonl`), is stored on the sticker as `caption {text, text_visible, model, version, png_sha, ts}` (an edited picture is captioned again), and never touches `review.*`. `GET /api/generations/{id}/captions` reads what is stored (no model, no consent; `missing` counts the cells still without one), `POST` writes the missing ones in the background (consent required, `{force}` captions again). The Studio shows them in the batch's fold in the sheet's own grid (**AI captions** in *Earlier batches*); an unnumbered chat request to "describe the stickers" / "what do they show" uses this batch-caption path after consent.

**Selected-sticker descriptions** (`vision/describe.py`, 2026-10-11). "What is the second sticker doing?", "what is he doing?" and "what about 4th sticker?" resolve within the same batch. `tools.describe` sends only the selected READY still to the configured vision model after `consent.require`, then streams a plain-language answer about visible pose, gesture, expression and objects; names and animations are not evidence for this answer. Each inspection is logged as `VLM_DESCRIBE`. The selected card is saved before inspection with `cards_first: true`; each text delta updates the existing chat-turn stream. `agent.js` keeps the card/video node intact while updating the text beneath it. Consent confirmation retains the original question and selection. A failed inspection keeps the card and reports that it could not inspect the still.

**Displaying the batch** (`resolver.display_request`, `graph.n_ask`). "Show all of them", "list every sticker" and "show the whole carousel" display the existing batch, even after a one-sticker card or UI selection. They bypass edit routing and semantic target picking, and create no generation plan or credit estimate.

**Vision model defaults** (`vision/judge.py`). An explicit `VISION_MODEL` wins. Cloud calls next use `MIRSAL_VISION_OPENAI_MODEL`, then the current session's forced choice, then the saved global cloud choice, `MIRSAL_LLM_MODEL`, and built-in Luna. Local calls use the forced session choice or normal local resolution. Explicit vision provider settings retain precedence; base-URL overrides apply only to local calls; otherwise vision follows the active LLM provider. Description failures retain the sticker card, show the sanitized provider error and end with a failed-inspection trace rather than "described the still". Cloud image capability is checked by the shared catalog allow-list before sending; local capability remains server-selected.

**Vision judge fallback order** (Haitham, 2026-10-12). Configure in `.env` with `MIRSAL_VISION_PROVIDER=openai` and `MIRSAL_VISION_OPENAI_MODEL=agnes-2.5-flash` (Nararouter) or `gpt-4o-mini` (OpenAI). The judge tries models in this order: (1) the configured cloud vision model (Nararouter's `agnes-2.5-flash` by default), (2) the general fallback `MIRSAL_LLM_FALLBACK` (default: `gpt-6-luna`) through Nararouter when the primary fails, (3) local LM Studio as last resort when both cloud options are unavailable. When local is also down, stickers are marked "unjudged" under the default `FAIL_CLOSED` policy. **Approved vision models:** Nararouter: `agnes-2.5-flash`, `agnes-3-flash`, `deepseek-v4.1-flash-free`, `muse-spark-1.3-contributor-free`, `stepfun-3.7-flash`. OpenAI: `gpt-4o-mini`, `gpt-6.1-sol`.

**Vision recovery** (`llm.complete_vision`, 2026-10-11). Captioning, still descriptions and pre-review retry once on the configured `MIRSAL_LLM_FALLBACK` through **Nararouter**, even when the chat pinned a direct OpenAI or another router/local model. The fallback uses `MIRSAL_CLOUD_URL` and `NARAROUTER_API_KEY`; its model id is routed as `nararouter:<id>` (the owner's configured fallback is `agnes-2.5-flash`). The first failed attempt and fallback share the original timeout budget. A visible streamed answer is never restarted; a request already using that same router fallback is not repeated. Disabled AI and an empty fallback setting do not recover automatically. The saved model choice stays intact. Successful vision ledger rows name the model that actually answered and add `fallback_from` / `fallback_reason`; if recovery also fails, the failure explains both attempts. Catalog listings describe available model ids, not this account's subscription entitlement. Tests cover the reported 403, direct OpenAI and local selections, bounded retries, partial streams, still descriptions and judge logging without real model calls.


**Description streaming** (`services/llm.py`). `complete(..., on_delta=...)` reads OpenAI-compatible completion SSE and emits visible content. Split `<think>` blocks and reasoning fields stay out of the answer. An endpoint returning ordinary JSON is accepted as one chunk. A cloud fallback may retry before any answer is visible, but cannot restart a partially streamed answer on another model.
