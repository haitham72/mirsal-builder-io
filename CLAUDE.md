# CLAUDE.md — Mirsal Builder / Mirsal Stickers (routing + rules)

**Status:** Active rebuild. Previous version: [`proposals/Mirsal-chat-emojis`](../Mirsal-chat-emojis) (archived backup; context-aware stickers for chat).

**Product:** high-quality, flashy **animated stickers**, **not emoji**. Emoji appear only as the ≥1 tag Telegram requires per sticker; there is no 100×100 custom-emoji output.

Live plan: **`phase_02.md` … `phase_05.md`** (one spec per phase not yet built) + `Phase_0N/` folders (Haitham's inputs and review gates per phase). **Each phase folder's `README.md` is the architecture of what that phase built** (`Phase_01/README.md` for Phase 1, built; its open items are the finish list in `Phase_01/CLAUDE.md`); the root `README.md` is the index. There is no `phase_01.md` any more.

## Structure

Two interfaces sharing one generation engine:
1. **Creator Mode** — explicit controls, prompt-driven, deterministic
2. **Conversational Mode** — natural-language creative direction, iterative

Never collapse into monolithic LLM prompt; separate creative intent → spec → generation → processing → validation → animation → persistence.

**Session hand-off:** read `HANDOFF.md` first, then the finish list in `Phase_01/CLAUDE.md`, before touching the UI or Telegram. The Studio views, the Pack wizard, edit-in-place, bulk delete, the out-of-bounds check, the animation cache and the Telegram send are built and tested on branch **`merge/generate-advanced`** (committed and pushed; `main` is not touched until Haitham says so). **Built on top of it, on Haitham's orders: Phase 2 offline (prompt lab, file jobs, slot reviewer), Phase 3A Postgres, the 3B lexical pool and the 3C photo core. Next is the live part of Phase 2 (Higgsfield MCP: S0, S3, S4, S6, S7 in `phase_02.md`), which needs a session where the Higgsfield tools exist; 3B vectors, 3D, 3E and Phases 4-5 do not start until Haitham confirms** (the order was swapped on 2026-10-01). Restart the server from `mirsal/.venv` before judging anything in the browser (the server now warns when it runs older code than the files on disk). Never commit a Telegram token (any token pasted in chat must be revoked) or `opencode.json` (API key, gitignored), and never `git add -A` blind.

## Rules

1. **Telegram sticker specs:** WEBM/VP9 + alpha (video); PNG/WEBP + transparency (static). Max 256 KB, 512×512, 30 FPS, 3s max. Every sticker tagged with ≥1 emoji.
2. **Phases (the build plan):** **Phase 1 (`Phase_01/`, built)**: the engine (prepared sheets → key/scale → stickers + WEBM) plus the desktop Sticker Builder UI over it (Parts D and E: video/GIF projects and the optional AI matte; `ref/` holds its design spec and mockup), the golden path with review gates (1F, rule 10), the **simple flow** (1G: type a request -> stickers -> Animate -> Add; History = the watch folders with Remove; the React gateway `mirsal/web/` is parked, not served) and Send to Telegram (1H, Part H) → **`phase_02.md` live generation** (prompt engine with template-locked prompts, VLM pre-review, and generation through **Higgsfield via its MCP connector** driven by an operator session, on the file store; the video always comes from the normalised video sheet) → **`phase_03.md` Postgres** (3A: stable IDs, reviews, search, LangSmith tracing; imports what Phase 2 wrote) and then the semantic sticker pool (3B), photo cutout stickers (3C), CapCut-style text template stickers (3D) and 3D parallax photos (3E) → `phase_04.md` Redis + LangGraph + intelligence (4A/4B/4C) → `phase_05.md` API + hardening (5A/5C) and the reference client (5B). Build only the phase you're given. Each `Phase_0N/` folder's CLAUDE.md lists that phase's inputs from Haitham and its review gates. The original `mvp plan.md` / `full plan.md` were absorbed into these phases and removed (they're in git history). The order of 2 and 3 was swapped on 2026-10-01; older notes saying "Phase 2 = Postgres" are stale.
3. **Generation engine is deterministic and independently testable** — never hide it behind conversational abstractions.
4. **Input types:** text, image, text+image, previous generation, previous stickers, event/topic, natural-language transformation.
5. **Default output:** 3×3 master (9 stickers), 2K → 512px final, transparent, 3s animation @ 30 FPS; all user-configurable.
6. **No dead stubs** — if a UI control exists, the backend is implemented.
7. **Plans are hand-off / next steps; the phase README is the architecture.** Once a step is built and verified, record it in that phase's `README.md` (as architecture: what exists, how it fits, the naming and contracts) and tick it in its `phase_0N.md` (a phase whose plan is fully built has its plan file removed, as `phase_01.md` was). A plan item is deleted only after Haitham approves that gate, so the plan thins out over time and is eventually removed. Updating a plan means **enhancing** it (findings, corrected assumptions, sharper next steps), never shrinking it. Every change in one phase must be checked against the following phase's plan and `Phase_0N/CLAUDE.md`, and those updated if it affects them.
8. **Lean dependencies + cross-platform.** The dev PC runs Windows (macOS also supported) and, since 2026-10-01, has proper internet and PyPI; the lean rules below still hold. Use the project venv `mirsal/.venv` (the Anaconda base env has a broken numpy). Stdlib first, minimal wheels, no CDN/npm at runtime (npm is dev/build-time only for `mirsal/web/`; the Python server serves the built `dist/`), `pathlib` only, no shell-specific commands, ffmpeg from PATH or `imageio-ffmpeg`. Anything fetched from the internet (wheels, Docker images, model weights) is fetched once on a connected machine and loaded from disk. `python -m mirsal doctor` is the single health check and each phase extends it. Details: `Phase_01/README.md`, "Restricted network / library policy".
9. **Naming convention:** inputs are one folder per variant, `img-NNN-<subject>/` and `vid-NNN-<subject>/` (paired by NNN), plus optional pre-sliced clips in `vid-NNN/slices/`; **the watch-folder names are final, never rename them** (History's Remove moves a folder pair to `out/trash/` on Haitham's click, and Restore puts it back under the same names). Outputs `<media>-<NNN>-<task_slug>-<key>.<ext>` in `mirsal/out/G00N/slices/`. Never open media files to judge them; use validators and metrics.
10. **The golden path is the spine** (`Phase_01/README.md`, "The golden path", checkpoint 1F). The flow is: request → plan with 1–5 tags + margin per cell (**G1**) → sheet → Python blocks bad cells → stills (**G2**) → video sheet from the approved stickers only (**G3**) → video → Python boundary check on every frame → animations (**G4**) → final pack (**G5**). Every phase keeps it working end to end. Python's blocks are final; a human approves or rejects at every gate (the VLM only pre-reviews); rejection never deletes; a sticker keeps its original `S#` through every stage. From Phase 3 (3A) every decision is a `reviews` row in Postgres (searchable) and is mirrored to LangSmith when tracing is on; until then it is a `history` line in `result.json`. Grids are 3×3 or 2×2 (user's choice); regenerating one sticker is a 1×1 through the same engine. **Hard truth:** request → external task id (Phase 2: written to `out/jobs/*.json` and `out/tasks/*.json` at `claim`, before waiting) → Postgres `tasks` row `{external_task_id, name_key}` (Phase 3) → dev lookup and key/semantic search (`phase_03.md`). **The Python/OpenCV verifier** (`engine/verify.py`, `Phase_01/README.md` "The verifier") runs at every stage, and its BLOCK verdicts are final.
11. **Delivery (Haitham, 2026-10-01): the product is an API / app, not this UI.** There is already a Mirsal app (Mirsal-Builder); everything under `mirsal/mirsal/console/` and `mirsal/web/` is a **sandbox / proposal** that drives and demonstrates the engine. Design every feature as an **engine function + a stable JSON contract first** (so the app can call it as an API) and the screen second; never put logic only in the browser. Studio edits, packs, jobs and Telegram sends must therefore be addressable by id and reproducible from their stored data.
12. **Docs are part of every MAJOR step (Haitham, 2026-10-01).** A major step (a phase or checkpoint, a new feature area, a renumbering, a change of provider, a changed contract) is not finished until, in the same step: `README.md` (architecture of what exists), `HANDOFF.md` (state, open list, next prompt), the affected `phase_0N.md` (tick, correct, enhance; remove what is stale), `CLAUDE.md` routing / rules and the affected `Phase_0N/CLAUDE.md` are updated, and the next phase's plan is checked. Stale statements are deleted, not left beside the new ones.
